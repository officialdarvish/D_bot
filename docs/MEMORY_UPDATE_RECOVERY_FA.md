# بررسی حافظه و اصلاح شکست آپدیت — 1.4.0 بیلد ۵

عدد RAM در داشبورد از MemTotal و MemAvailable در /proc/meminfo محاسبه می‌شود؛ مصرف کل VPS است و به‌تنهایی مصرف ربات یا ارتباط مستقیمی با تعداد کاربران فعال نشان نمی‌دهد. بررسی واقعی به تفکیک کانتینر و قبل/بعد روی همان VPS هنوز انجام نشده است.

## ایراد مشخص در آپدیت

فایل‌های install.sh و چند اسکریپت مدیریت در مخزن مجوز 644 داشتند ولی نصاب آن‌ها را به 755 تغییر می‌داد. بررسی git status در اجراکننده، این تغییر مجوز را ویرایش سورس حساب می‌کرد. آزمون با مخزن Git واقعی این حالت را بازتولید می‌کند. اکنون فایل‌های اجرایی با 755 ثبت شده‌اند؛ بررسی وضعیت و checkout نیز به‌صورت محدود به همان فرمان، core.fileMode=false دارند. ویرایش واقعی محتوای فایل‌ها همچنان مانع آپدیت خودکار می‌شود. بدون لاگ یا اطلاعات مستقیم VPS نمی‌توان گفت خطای گزارش‌شده دقیقاً همین علت را داشته است.

پیام قدیمی Previous source recovery: False حتی پیش از تغییر نسخه صادر می‌شد و به معنی قطعی خرابی بازیابی نبود. اکنون مرحله، کد خروج، دلیل دسته‌بندی‌شده و یکی از وضعیت‌های زیر ذخیره و در وب نمایش داده می‌شوند:

| وضعیت | معنی |
| --- | --- |
| not_needed | تعویض سورس/کانتینر شروع نشده و بازیابی لازم نبوده است |
| restored | سورس و ایمیج‌های قبلی بدون بیلد مجدد برگشته و سلامت API تأیید شده است |
| failed | بازیابی یا سلامت آن قابل تأیید نبوده است |

پیش از تغییر نسخه، شناسه ایمیج کانتینرهای API و bot با تگ‌های بازیابی حفظ می‌شود. تأیید سلامت نسخه جدید علاوه بر HTTP موفق، به مطابقت شماره نسخه و بیلد پاسخ /health با هدف آپدیت وابسته است. خطای تعویض جزئی سورس نیز مسیر بازیابی را فعال می‌کند. شکست نسخه جدید با همان ایمیج‌های محلی و --no-build --pull never بازیابی می‌شود؛ ساخت مجدد سنگین نسخه قبلی حذف شده است. فایل Compose بازیابی در پوشه خصوصی میزبان زیر /var/lib/dbot-web-updater نگهداری می‌شود، نه پوشه قابل‌نوشتن کانتینر وب. بازیابی خودکار دیتابیس پس از مهاجرت انجام نمی‌شود؛ بکاپ برای تصمیم آگاهانه نگه داشته می‌شود.

خروجی فرمان‌ها حتی بدون journald در .web-update/update-<job-id>.log روی VPS می‌ماند. هر فرمان حداکثر 64 KiB از انتهای خروجی را نگه می‌دارد؛ پردازش خروجی به فایل موقت انجام می‌شود. اطلاعات خام فرمان‌ها از API عمومی/وب نمایش داده نمی‌شود. کمبود حافظه احتمالی، دیسک پر، خطای DNS و اتصال از خروجی محلی به دلیل‌های ثابت تبدیل می‌شوند؛ کد 137 به‌تنهایی اثبات OOM نیست.

## تغییرات حافظه

| بخش | تغییر |
| --- | --- |
| تاریخچه منو | با Redis سالم، کپی دوم تاریخچه هر کاربر در حافظه Python نگه داشته نمی‌شود؛ fallback محدود و قابل انقضا برای قطع Redis باقی است |
| قفل منو | قفل‌های بدون کاربر/منتظر از طریق weak reference آزاد می‌شوند؛ هم‌زمانی یک کاربر همچنان سریالی است |
| ویدیوی آموزش | فایل تا 50 MiB به‌جای BytesIO کامل، در فایل موقت دیسکی دانلود و در قطعه‌های 64 KiB ارسال و بسته می‌شود |
| QR | لایه‌ها و تصویرهای واسطه بلافاصله آزاد می‌شوند؛ پیک RAM فرایند آزمایشی از 116.29 به 84.15 MiB رسید، با SHA-256 یکسان محتوای پیکسلی |
| دیتابیس | پیش‌فرض هر فرایند: ۳ اتصال ماندگار و ۵ overflow، به‌جای ۱۰+۲۰؛ مقدار صریح صفر برای overflow هم درست حفظ می‌شود |
| HTTP و همگام‌سازی | پیش‌فرض Sanaei برابر ۱۲ اتصال و ۴ keep-alive، تلگرام ۳۰ اتصال، Redis برابر ۲۰ و همگام‌سازی هم‌زمان دو سرور است |
| تخصیص‌دهنده | MALLOC_ARENA_MAX=2 در کانتینرهای Python، قابل تغییر از محیط |
| ساخت | یک ایمیج مشترک برای API و bot؛ فقط API آن را می‌سازد؛ ساخت‌ها سریالی و heap پیش‌فرض Node برابر 768 MiB است؛ export یک worker دارد |

اندازه pool سقف تنظیمات است و به معنی ساخته‌شدن همه اتصال‌ها از ابتدا نیست. تنظیمات صریح قدیمی در .env حفظ می‌شوند؛ برای استفاده از پیش‌فرض سبک‌تر، مقادیر DB_POOL_SIZE=3 و DB_MAX_OVERFLOW=5 و محدودیت‌های HTTP فوق را در تنظیمات موجود انتخاب کنید. اگر بار هم‌زمان بالاست، این سقف‌ها باید با زمان انتظار و تست بار همان VPS تنظیم شوند. برای Redis و PostgreSQL سقف سخت حافظه یا سیاست حذف خودکار داده مالی/FSM اضافه نشده است.

اندازه‌گیری QR با دو فرایند مستقل، Pillow و وابستگی‌های فعلی، یک لینک و تصویر پیش‌فرض انجام شد. کاهش حدود 27.6 درصد مربوط به پیک RSS همان تست است؛ کاهش مصرف کل VPS از 1.8 GiB به مقدار خاصی اندازه‌گیری یا تضمین نشده است.

## تشخیص روی VPS

پس از نصب این بیلد:

```bash
sudo dbot memory
```

این فرمان فقط وضعیت حافظه میزبان، docker stats کانتینرهای پروژه و وضعیت OOM/خروج را می‌خواند؛ محتویات .env، کلیدها و اطلاعات کاربران را چاپ نمی‌کند. در نسخه فعلی قدیمی، free -m و docker stats --no-stream نیز همین بررسی اولیه را ممکن می‌کنند.

برای دریافت اصلاح اجراکننده قدیمی، یک‌بار sudo dbot update روی همان VPS لازم است. ساخت هنوز به RAM آزاد و فضای دیسک نیاز دارد؛ هیچ swap یا محدودیت سخت حافظه‌ای خودکار روی میزبان ایجاد نمی‌شود. تست زنده Docker/systemd و ظرفیت VPS کاربر انجام نشده است.
