# اصلاح توقف آپدیت هنگام نصب Xray

لاگ ارسالی نشان می‌دهد درخواست دانلود ZIP با چند پاسخ HTTP 503 مواجه شده و پس از حدود ۴۵۰ ثانیه شکست خورده است. گزینه connect-timeout فقط برقراری اتصال را محدود می‌کرد؛ برای کل انتقال مهلتی وجود نداشت و چهار retry باعث پنج تلاش طولانی می‌شد. این لاگ خطای اجرای باینری ARM64 یا پردازنده را نشان نمی‌دهد و برای تعیین منشأ پاسخ 503 در مسیر شبکه کافی نیست.

## مسیر پیش‌فرض جدید

باینری Xray از ایمیج رسمی چندمعماری زیر کپی می‌شود:

```text
ghcr.io/xtls/xray-core:26.9.9@sha256:45338c4df61fda061c47ce62aafda6c5d7d59cbdefc33f2e335d8b0c748b748a
```

نسخه فعلی پروژه حفظ شده و digest مجموعه ایمیج‌ها ثابت است. Docker نسخه مناسب معماری مقصد را انتخاب می‌کند. مسیر باینری در Dockerfile رسمی همان نسخه بررسی شده است. دیگر curl و دانلود ZIP از GitHub Releases در مسیر پیش‌فرض اجرا نمی‌شود. لایه Xray از نصب وابستگی‌های پایتون و تغییرات سورس جدا شده است؛ بنابراین تغییر requirements یا کد، به‌تنهایی Xray را دوباره دانلود نمی‌کند. پس از کپی، دستور xray version در ایمیج مقصد اجرا می‌شود.

API و bot تنظیمات build یکسان دارند. اگر build شکست بخورد، اسکریپت آپدیت به مرحله بررسی سلامت ادامه نمی‌دهد و پیام موفقیت نمایش نمی‌دهد.

منابع رسمی بررسی‌شده:

- https://github.com/XTLS/Xray-core/pkgs/container/xray-core/1225470370?tag=26.9.9
- https://github.com/XTLS/Xray-core/blob/v26.9.9/.github/docker/Dockerfile

## بروزرسانی معمول

پس از جایگزینی فایل‌ها، در پوشه پروژه، با حفظ فایل محیط و دیتابیس اجرا کنید:

```sh
docker compose build api bot && docker compose up -d --no-build api bot
```

به no-cache نیازی نیست. دفعه اول، لایه‌های ایمیج رسمی باید دریافت شوند. سرعت کل build همچنان به دسترسی رجیستری، npm، PyPI، مخازن سیستم و منابع VPS بستگی دارد؛ برای کل build زمان ثابت یا دانلود تضمین‌شده اعلام نمی‌شود.

## مسیر ZIP و نصب محلی Xray

اگر رجیستری رسمی در دسترس نبود، مسیر archive نیز پشتیبانی می‌شود. فایل رسمی نسخه 26.9.9 را روی دستگاهی با دسترسی مناسب دریافت و بدون استخراج در یکی از مسیرهای زیر قرار دهید:

| معماری VPS | مسیر فایل در پروژه |
| --- | --- |
| ARM64 | build/xray/26.9.9/Xray-linux-arm64-v8a.zip |
| AMD64 | build/xray/26.9.9/Xray-linux-64.zip |
| ARMv7 | build/xray/26.9.9/Xray-linux-arm32-v7a.zip |

نام فایل رسمی را حفظ کنید. انتخاب نسخه و معماری اشتباه، ZIP خراب یا باینری غیرقابل اجرا باعث توقف با پیام روشن می‌شود. سپس اجرا کنید:

```sh
XRAY_SOURCE=archive docker compose build api bot && docker compose up -d --no-build api bot
```

برای استفاده دائمی از این روش، XRAY_SOURCE=archive را در فایل .env قرار دهید. اگر فایل محلی وجود داشته باشد، این مرحله هیچ درخواست شبکه‌ای برای Xray انجام نمی‌دهد. این قابلیت فقط نصب Xray را آفلاین می‌کند؛ سایر تصاویر و وابستگی‌ها همچنان به شبکه یا کش قبلی نیاز دارند.

اگر در حالت archive فایل محلی موجود نباشد، ابتدا کش نسخه و معماری بررسی می‌شود؛ در نبود کش معتبر، حداکثر دو دانلود انجام می‌شود. هر تلاش مهلت اتصال ۸ ثانیه و مهلت کل انتقال ۶۰ ثانیه دارد؛ انتقال راکد یا بسیار کند نیز قطع می‌شود. فاصله دو تلاش فقط ۲ ثانیه است. کش BuildKit پس از اعتبارسنجی ذخیره می‌شود و فایل ناقص جای فایل سالم را نمی‌گیرد. خطای دانلود به ساخت ایمیج فاقد Xray تبدیل نمی‌شود.

## اعتبارسنجی

۱۱ تست با اجرای واقعی اسکریپت shell، ZIPهای آزمایشی و پاسخ‌های شبکه شبیه‌سازی‌شده موفق بودند: 503 مداوم، بازیابی پس از 503، فایل ناقص، کش سالم و خراب، فایل محلی، نسخه اشتباه، انتخاب نام فایل معماری و توقف آپدیت پس از شکست build. نحو shell و فایل‌های لازم پروژه نیز بررسی شدند. خروجی وب این نسخه تغییری ندارد و عین نسخه قبلی حفظ شده است.

Docker در محیط بررسی نصب نیست؛ بنابراین ساخت کامل ایمیج، pull واقعی رجیستری و اجرای باینری واقعی ARM64/AMD64 روی VPS اینجا انجام نشده است.
