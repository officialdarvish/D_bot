> D BOT companion adjustments: the authenticated `/api/v1/connect/capabilities` endpoint advertises digital products only when `ALLOW_DIGITAL_MANUAL_RECEIPTS=1` is explicitly configured (default 0). Product kind remains `digital`. The local API port defaults to 8095 to avoid a D BOT port collision. Follow [the D BOT connection guide](../../docs/DARVISH_BRIDGE_CONNECTION_FA.md) for this integration. The original MVP documentation follows below.

> تغییرات نسخه همراه D BOT: قابلیت محصول دیجیتال فقط با فعال‌سازی صریح `ALLOW_DIGITAL_MANUAL_RECEIPTS=1` اعلام می‌شود و پیش‌فرض غیرفعال است. نوع محصول دیجیتال باقی می‌ماند. پورت محلی API این نسخه 8095 است. راهنمای اتصال بالای این متن، تنظیمات نسخه همراه را توضیح می‌دهد؛ متن زیر مستندات MVP اولیه است.

# Darvish Bridge | دارویش بریج

**نسخه ۱٫۰ آزمایشی (MVP)** — پلتفرم فارسی مدیریت سفارش، بررسی دستی تصویر رسید، ثبت حسابداری فروشندگان و مدیریت درخواست‌های تسویه، با ربات و مینی‌اپ تلگرام.

> این بسته **کد واقعی و قابل‌اجرا** است؛ نه صرفاً طرح گرافیکی. اما «محصول نهایی آماده بهره‌برداری مالی عمومی» نیست. برای استفاده عمومی، باید امنیت، تعهدات قانونی، کنترل دریافت وجه، زیرساخت پشتیبان و اتصال واقعی D Bot بررسی و تکمیل شوند.

## امکانات پیاده‌سازی‌شده

- ثبت‌نام فروشنده از طریق ربات یا مینی‌اپ و تأیید/رد مدیر
- ایجاد کلید اختصاصی اتصال ربات فروشنده، امکان ابطال کلید، وب‌هوک امضاشده
- API ساخت سفارش توسط ربات فروشنده، شناسه سفارش خارجی یکتا و ساخت تکراری ایمن
- مقصدهای دریافت متعدد با واحدهای قابل پشتیبانی و **انتخاب تصادفی از حساب‌های فعال همان واحد**
- مشاهده سفارش در ربات توسط خریدار و ارسال عکس رسید در همان گفت‌وگو
- صف بررسی رسید برای مدیر، مشاهده عکس، رد یا تأیید دریافت واقعی
- جلوگیری از تأیید تکراری و ثبت دوباره درآمد
- اعلام نتیجه به خریدار، فروشنده و ربات متصل
- **تحویل خودکار پیام/مشخصات سفارش** از فیلد اختیاری `delivery_message` پس از تأیید، یا اعلام تأیید به وب‌هوک D Bot برای تحویل توسط خود D Bot
- دفترکل دوطرفه با اعداد صحیح و کارمزد قابل تنظیم برای هر فروشنده
- موجودی آزاد و رزروشده، درخواست تسویه، تأیید، رد، ثبت شناسه انتقال واقعی
- چرخه زمانی روزانه قابل‌تنظیم برای گروه‌بندی درخواست‌های تسویه (بدون اجرای خودکار واریز)
- پنل راست‌چین فارسی در تلگرام برای مدیر و فروشنده
- اختلافات، اعلان‌های تلگرامی، گزارش رویدادهای حساس و صف اعلان/وب‌هوک با تلاش مجدد
- تعلیق فروشنده، تغییر کارمزد، تلاش مجدد تحویل و ثبت بازگشت وجه پس از تأیید انتقال واقعی
- تست خودکار سناریوهای اصلی و Docker Compose برای اجرا

## محدودیت مهم دامنه نسخه

این پروژه بنا به درخواست، **فقط مسیر عکس رسید و تأیید دستی** را در هسته اجرایی دارد و هیچ یک از روش‌های ستاره/درگاه خودکار/واریز خودکار را پیاده نمی‌کند. دارایی‌ها و حساب‌های دریافتی باید واقعاً متعلق به ساختار مجاز کسب‌وکار باشند؛ انتخاب تصادفی شماره/آدرس برای دورزدن محدودیت‌ها طراحی نشده است.

**قانون تلگرام:** فروش خدمات و محصولات *دیجیتال* داخل بات‌ها و مینی‌اپ‌ها باید طبق مقررات تلگرام با Stars انجام شود. در نتیجه، آداپتور «عکس رسید» پروژه برای `physical` و `offline_service` فعال است و برای `digital` به‌عمد خطای ۴۲۲ برمی‌گرداند. این موضوع به‌خصوص درباره فروش اشتراک‌های VPN در D Bot مهم است. می‌توان از دارویش برای مدیریت سفارش و پشتیبانی استفاده کرد، اما نباید انتظار داشت در همین مسیر، فروش درون‌تلگرامی کالای دیجیتال با کارت/رمزارز جایگزین شود. منبع رسمی: https://core.telegram.org/bots/payments-stars

## راه‌اندازی روی VPS با داکر

۱. پیش‌نیاز: دامنه با HTTPS، VPS لینوکسی، Docker و Docker Compose، ربات ساخته‌شده با BotFather، شناسه عددی مدیر و دامنه وب‌هوک فروشنده (در صورت نیاز).

۲. فایل نمونه تنظیمات را کپی کنید:

```bash
cp .env.example .env
```

۳. مقادیر زیر را در `.env` واقعی تنظیم کنید:

```env
TELEGRAM_BOT_TOKEN=BOT_TOKEN_FROM_BOTFATHER
ADMIN_TELEGRAM_IDS=YOUR_NUMERIC_TELEGRAM_ID
APP_SECRET=LONG_RANDOM_SECRET_AT_LEAST_32_CHARS
DB_PASSWORD=LONG_UNIQUE_DB_PASSWORD
PUBLIC_BASE_URL=https://bridge.example.com
WEBHOOK_ALLOWED_HOSTS=merchant.example.com
SETTLEMENT_CYCLE_HOURS=24
```

برای ساخت کلید امن می‌توانید اجرا کنید:

```bash
python -c "import secrets;print(secrets.token_urlsafe(48))"
```

۴. سرویس‌ها را اجرا کنید:

```bash
docker compose up -d --build
docker compose ps
docker compose logs --tail=80 api bot
```

۵. روی سرور، آدرس `127.0.0.1:8000` را پشت یک reverse proxy دارای HTTPS منتشر کنید؛ **پورت داخلی پایگاه داده را منتشر نکنید**. نمونه پیکربندی Caddy در `docs/INSTALL_FA.md` وجود دارد.

۶. در BotFather، برای ربات خود دکمه/منوی Mini App را با آدرس `https://bridge.example.com` تنظیم کنید. ورود مینی‌اپ صرفاً با `Telegram.WebApp.initData` معتبر انجام می‌شود؛ بازکردن آدرس در مرورگر معمولی ورود مدیریتی نمی‌دهد.

۷. از داخل ربات، `/start` را بزنید. فروشنده با `/register نام فروشگاه` ثبت‌نام می‌کند. مدیر در پنل درخواست را تأیید می‌کند. سپس مدیر مقصد دریافت را تعریف می‌کند، فروشنده کلید رباتش را می‌سازد و D Bot از API سفارش ثبت می‌کند. خریدار با `/order شناسه` سفارش را باز می‌کند و تصویر رسید می‌فرستد؛ مدیر تصویر را در تلگرام یا مینی‌اپ بررسی می‌کند.

**نکته استقرار:** برای اجرای محلی می‌توان `DATABASE_URL=sqlite:///./darvish.sqlite3` انتخاب کرد، اما در سرور اصلی از PostgreSQL (پیش‌فرض Compose) استفاده کنید. مقدار `DB_PASSWORD` در فایل `.env.example` خالی است تا ناخواسته از رمز ثابت استفاده نشود.

## دستورات ربات

| دستور | کارکرد |
|---|---|
| `/start` | منو و دسترسی مینی‌اپ |
| `/order <شناسه>` | بازکردن سفارش و فعال‌شدن ارسال عکس رسید |
| `/register <نام>` | درخواست فروشندگی |
| `/merchants` | نمایش فروشگاه‌های متعلق به کاربر |
| `/wallet <شناسه‌فروشنده>` | مشاهده موجودی آزاد و رزروشده |
| `/settle <شناسه‌فروشنده> <مبلغ> <ارز> <مقصد>` | درخواست تسویه با مبلغ اعشاری |
| `/dispute <شناسه‌سفارش> <توضیح>` | ثبت اختلاف خریدار |
| `/paysupport` | راهنمای پشتیبانی پرداخت |
| `/pending` | فقط مدیر: سفارش‌های در انتظار رسیدگی |
| `/settlements` | فقط مدیر: درخواست‌های تسویه |
| `/paid <شناسه‌تسویه> <شناسه‌انتقال>` | فقط مدیر: ثبت پرداخت انجام‌شده برای درخواست از پیش تأییدشده |

### ترتیب کار مدیر در مورد رسید

۱. بررسی تصویر؛ ۲. **کنترل مستقل وجود واریز واقعی در حساب یا کیف پول مقصد**؛ ۳. تأیید یا رد از روی پیام رسید. تأیید مدیر، ثبت درآمد و ارسال پیام تحویل یا وب‌هوک را فعال می‌کند.

### ترتیب تحویل

- اگر هنگام ساخت سفارش `delivery_message` داده شده باشد، **متن تحویل** پس از تأیید برای خریدار در تلگرام ارسال می‌شود و سفارش `fulfilled` می‌گردد.
- در غیر این صورت، رویداد `order.approved` به وب‌هوک فروشنده ارسال می‌شود تا **ربات فروشنده** اطلاعات واقعی سرویس را ایجاد و تحویل دهد. بعد باید وضعیت را به `fulfilled` یا `failed` گزارش کند.
- اگر ربات مقصد وب‌هوک نداشته باشد و `delivery_message` نیز خالی باشد، سفارش در `fulfillment_pending` باقی می‌ماند. این وضعیت را باید عملیاتی پیگیری کرد.

## ساختار پوشه‌ها

```text
darvish_bridge/
├─ app/
│  ├─ api.py          # REST API و ورود تلگرام
│  ├─ bot.py          # ربات و صف اعلان/وب‌هوک
│  ├─ config.py       # تنظیمات و واحدهای دارایی
│  ├─ database.py     # اتصال پایگاه داده
│  ├─ models.py       # جداول و موجودیت‌ها
│  ├─ schemas.py      # اعتبارسنجی درخواست‌ها
│  ├─ security.py     # امضا/احراز هویت
│  └─ services.py     # منطق سفارش، دفترکل و تسویه
├─ web/                # پنل مینی‌اپ فارسی
├─ examples/           # نمونه آداپتور D Bot
├─ tests/              # تست‌های خودکار
├─ docs/               # مستندات فارسی
├─ docker-compose.yml
├─ Dockerfile
└─ .env.example
```

## اجرای تست‌ها

```bash
pip install -r requirements-dev.txt
pytest -q tests
```

تست‌ها از فایل SQLite مستقل استفاده می‌کنند و به تلگرام یا پایگاه داده اصلی متصل نمی‌شوند.
